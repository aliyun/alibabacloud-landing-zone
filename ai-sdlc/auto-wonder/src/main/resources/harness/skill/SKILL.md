# AutoWonder 工作空间初始化

在 Chief 当前会话空间初始化模板。一次完成模板、项目变量、部署能力、仓库及权限、默认执行器配置，成功后引导客户启动执行器，再新建工单。不创建空间或业务工单，不自动启动交付。

本版本依赖 [平台初始化契约](references/platform-contract.md) 中的专用能力。工具不可用时说明需要升级平台，停止初始化；不回退到本机 MCP、私有 HTTP 或直接写入工具。

## 执行入口与客户提问边界

用户要求初始化空间、继续初始化或补充初始化资料时，先完整读取本 Skill 及内嵌或随附的 `var.md`，再提问或调用初始化工具。不要只看技能简介或沿用历史问卷；相关文档无法读取时说明初始化指引暂不可用并停止，不自行编造表单。

不得根据工具 schema、variables 占位符或历史问卷另拟客户问题。内部配置字段不是客户问卷：仓库权限、额外技能、模型覆盖等按本 Skill 的固定规则处理，不另行索取。客户端选择必须使用内置提问工具弹出单选卡，按下文规则展示 Qoder / Qoder CN；客户已明确回答且仍可用时直接复用。提问工具不可用时说明阻塞，不改成正文二选一。随后只使用 `var.md` 的五部分带示例客户模板，不输出内部七变量清单。

本 Skill 的提问和执行约束仅适用于空间初始化；切换到其他 Skill 或通用任务后按对应规则执行，不延续初始化问卷及提问限制。初始化专用工具的执行方式以本 Skill 和服务端权限校验为准，不因此豁免其他管理操作的确认或权限校验。

## 引导进度

面向客户固定展示以下 2 步，按实际结果推进，不按变量数、工具调用数或对话轮数计步：

1. **提供初始化资料**：通过客户端选择卡选择执行器客户端，再按现有精简项目资料清单提供仓库、构建测试、数据库及部署信息。已知信息直接复用，补充缺项仍属于本步。
2. **一次完成空间配置**：一次预检冻结模板、变量、默认执行器、仓库关系与权限、部署 Skill 绑定及必要发布，一次调用初始化工具完成全部业务写入。仅统一批次 `status=SUCCEEDED` 才完成本步。

首次从第 1 步开始；进入步骤或要求操作时显示：

> 共 2 步｜当前第 i 步：步骤名称｜已完成 C 步｜剩余 R 步（含当前未完成步骤）

R=2-C。草稿、补问、预检、重试及部署 Skill 准备不增加步骤。后台技术步骤与计数仅用于查漏和恢复，不直接拼接客户进度。续聊按真实批次结果恢复，不沿用旧对话步数。统一批次成功后显示“共2步，已完成2步，剩余0步”，表示空间配置初始化完成，此时 `result.stage=RUNTIME_PENDING`，不代表执行器在线或 `READY`。启动执行器和交付就绪检查属于初始化完成后的流程，不计入这 2 步。

### 草稿处理保持静默

草稿查询、创建、恢复、保存和版本管理均为后台内部动作，不是客户步骤，不需要客户确认。开始时后台调用 `autowonder.get_workspace_onboarding` 查询当前用户、当前空间的记录：有记录则恢复已有信息与真实进度；已完成的记录按实际就绪状态说明，不重新初始化。仅在确实没有记录（`HARNESS_ONBOARDING_NOT_FOUND` 或空列表）时，自动调用 `autowonder.prepare_workspace_onboarding` 创建草稿，携带稳定的 `requestKey`（`workspace-initialization`，同一用户和空间重试复用）及初始 `draft`。更新已有草稿使用其 `onboardingId` 与 `expectedVersion`，不另建记录。

正常情况下，聊天正文不得出现“没有找到草稿”“需要新建草稿”“正在恢复草稿”或草稿ID、版本等内部过程；直接展示客户步骤和当前需要提供的信息。不要先发一条草稿说明再继续，也不要让客户发送“创建草稿”或为草稿操作点击确认。权限、网络、保存失败等真实错误不能当作没有记录；确实阻塞流程时用客户能理解的话说明影响和恢复方式，不暴露内部草稿机制，不虚报成功。

## 第 1 步：提供初始化资料

部署信息仅在初始化前的文本清单收集，不生成「部署要求」弹窗。不向客户索取冒烟测试的地址、入口、命令或用例，也不把这些信息列为缺项。

客户端是初始化全程唯一允许的弹窗问题。历史消息或旧问卷中出现的仓库注册时机、数据库、部署、MR/PR 选择题均已废弃，不再要求作答或继续该问卷；继续会话时按本规则转入文本资料清单，复用已知信息。

初始化前先完成客户端选择卡，再立即发送 var.md 中完整的带示例项目资料填写模板，收到完整反馈后才预检和执行初始化。不得将模板改写为只有字段名和空白值的清单。不得在选择卡提交后立即初始化，也不得先导入带占位符的模板再收集信息。读取模板、保存草稿和只读核实不属于初始化执行，可以提前调用。

初始化全程不得询问「项目形态」「项目类型」或含义相同的分类题。已有问卷中的分类题不作为继续流程的条件。仓库绑定完成后，以当前项目实际绑定的不同仓库数量判断：一个为单仓，多个为多仓，尚无绑定则保持待定。后续配置直接使用客户提供的仓库职责、技术栈和部署信息。

客户信息只允许从以下固定的五个题目中收集。已知项直接复用，条件不适用的题跳过，补充同一题的缺项不增加题目。执行器客户端使用选择卡。项目资料按 var.md 中已确认的五部分客户模板（代码仓库、构建与测试、数据库脚本、数据库配置、部署）统一用一份聊天正文填写清单收集，数据库、部署和合并目标不得生成弹窗。清单之外的题须先经流程维护者确认并更新本清单。

1. 执行器客户端：初始化前选择 Qoder 或 Qoder CN。
2. 仓库信息：项目资料阶段一次收集地址、默认分支、职责和依赖。
3. 构建与单元／组件测试：合并收集命令、目录和适用范围。覆盖率直接沿用模板 Skill 的 config 固定配置，不询问、不推断、不根据客户反馈修改。
4. 数据库：按下文确认是否涉及。涉及时在同一题下收集连接配置引用和脚本约定。
5. 测试环境部署：用一段说明收集逐仓库目标分支、部署脚本或 Skill 名称及必要参数；其余实现细节从实际脚本或 Skill 核实，不扩展成复杂表格。

不生成「后端栈」「前端栈」「MR 平台」「覆盖率」或同义题，也不要求客户用正文回答这些题。构建和测试直接核实实际命令，MR/PR 采用模板固定规则。模型目录缺失、未知变量或其他清单外缺项时，报告阻塞及原因并保存进度，等待维护者处理。完整资料提交且统一预检通过后直接初始化，不追加确认题或行动计划。

1. 使用内置 MCP 的 `autowonder.list_harness_templates` 读取目录，自动选用本 Skill 随附的官方「软件研发交付小队」模板（稳定标识 `software-delivery`），并保存到引导草稿。已有引导沿用同一模板的已记录版本，已导入时继续未完成步骤。删除「模板」问题卡及其预览、推荐或自定义选项。模板名称与版本在执行前的配置摘要中展示。默认模板不可用时报告并停止，不让客户改选其他模板。
2. 读取模板版本、摘要及完整 variables 声明。客户端选择卡提交后，立即按下文和 [var.md](var.md) 发送一份可复制清单，一次收集资料。已知信息直接复用；缺项仍在同一清单下补齐。此时不得执行初始化。
3. 信息齐全后整理完整 `variableValues`：键为原始完整 token，值为最终配置文本。不适用须有明确依据；覆盖率沿用模板 config，MR/PR 和只读冒烟沿用固定规则。同步整理 `configurationChanges`，仅含 `repositories`、`relations`、`repoPermissions`、`skillBindings`。逐仓库明确名称、地址、默认分支和职责；关系明确 `from`/`to`（依赖方→被依赖方）；逐仓库逐模板角色明确 READ/WRITE 权限，使用模板角色码，不授予 ADMIN。部署 Skill 引用客户已提供、已发布的真实名称，并核实实际版本和参数；工程脚本部署不要求额外 Skill。

## 第 2 步：一次完成空间配置

调用 `autowonder.preview_workspace_initialization`，传入原模板预检参数、完整 `variableValues` 和 `configurationChanges`，一次冻结全部配置。缺失、未知、空值、未解析占位符或冲突必须先处理，不导入空模板，不将后续绑定拆成独立操作计划。

展示下文的简洁方案和后续指引后，直接调用 `autowonder.initialize_workspace(snapshotId, snapshotHash)`。无需客户再次回复确认或点击行动计划。服务端在实例副本中替换变量，完成模板 Skill、SDLC、数字人、小队、默认执行器、仓库关系与角色权限、部署 Skill 绑定及必要发布；母版不变，不再调用变量替换或单独配置应用工具。

通过 `autowonder.get_workspace_initialization(runId)` 查询同一批次。只有统一批次 `status=SUCCEEDED` 才宣称空间配置初始化完成；其 `result.stage=RUNTIME_PENDING`，不宣称执行器在线。失败或未知按原批次恢复，不重复询问资料，不重新初始化。

## 默认执行器配置

小队及成员配置完成后，自动为模板小队的每位数字人创建一个默认执行器，包括无 SDLC 的数字人；不包含 Chief。此操作纳入同一空间初始化批次。

- 名称：数字人名称直接拼接“默认执行器”。
- 上下文窗口：1M（`contextWindow="1000000"`）。
- 思考深度：中等（`reasoningEffort="medium"`）。
- 最大并行任务：10（`maxConcurrentDispatches=10`）。
- 记忆模式：平台推荐的平台记忆（当前 `memoryMode="platform"`）。
- 模型：代码评审工程师使用最新 GLM Flash 模型；其余数字人使用最新 DeepSeek-Flash 模型。按模板稳定角色码识别代码评审，不按可修改的显示名称猜测。

每次出执行器类型问题卡前，调用 `autowonder.list_executor_client_kinds` 获取当前可创建类型。必填单选题按固定顺序展示第一项「Qoder」（值为 `QODER_CLI`），第二项「Qoder CN」（值为 `QODER_CN_CLI`），仅展示返回列表中可用的对应项。选项名称严格使用上述纯文本，不添加 CLI、下划线、链接或其他后缀；提交给平台时使用对应的值。不添加推荐、默认选项或自定义选项，也不根据现有执行器推断。列表不可用时暂停此步，不用静态列表代替。客户已明确指定且仍在列表中时直接复用。选定后调用 `autowonder.get_executor_launch_options` 读取启动选项和实时模型目录，解析实际模型 ID 并冻结到快照。不得使用 auto、GLM 主系列或 DeepSeek-Pro 替代。目录仅有兜底值、模型缺失或“最新”无法可靠判断时，先提示补齐目录或让用户明确选择具体版本，不能声称兜底版本就是最新。

预检摘要包含各执行器名称、客户端、模型和上述配置；执行时使用冻结值，模型失效则报告失败，不静默换型。同一数字人下同名且配置一致可复用，不一致则报告冲突；保留其他执行器，重试不重复创建。执行器全部创建或复用成功只是统一批次成功的必要条件，仓库、权限、绑定及必要发布也须成功。这里只创建平台执行器记录，不注册或启动本机进程，不承诺在线。

## 初始化前的项目资料收集

在客户端选择卡之后、初始化执行之前读取模板 variables 声明，并直接复用 [var.md](var.md) 中「客户填写模板」标题之后、下一节「Chief 内部处理规则」之前的完整正文作为唯一客户模板。保留五部分结构、填写说明及每部分的具体示例，包括仓库与依赖、构建测试命令、数据库脚本、两种数据库配置读取方式、工程脚本和部署 Skill 两种部署示例。不得自行摘要、另拟空白表单，或用空值、下划线、「请填写」替换示例；客户尚未提供的项保留原示例并明确其只是待替换的填写参考，不能据此预检或初始化。已确认的实际信息可替换对应示例并标明已提供，不编造客户配置。

发送前核对：五部分均有具体参考值或客户已确认的实际值；示例未被当作客户资料；未夹带内部变量映射和执行规则。将模板单独作为一条 Chief 消息发送，客户可用现有消息复制按钮一键复制；进度与用途解释放在前一条消息，不拆成多个清单或后续弹窗。续聊若已经发出空白清单，补发带示例的完整模板并复用客户已提供的信息，不要求重新选择客户端或重复回答。新增变量先核对能否复用清单内已有资料，需要额外提问时交由流程维护者确认。

仅支持完整模板初始化。删除「交付范围」「部署范围」和「代码仓库何时提供」选择题，不提供只导入模板或只交付代码的模式。默认包含目标环境部署，仓库和必需部署信息统一在初始化前的项目反馈清单中收集，缺项先补齐。只执行部署和部署结果判定，不做独立只读冒烟，不收集冒烟地址。将只读冒烟变量固定填为「不适用：本空间不执行独立只读冒烟，部署结果按已确认的版本和健康判定核对」，并在预检中核对实例步骤和检查项无需冒烟证据即可完成。

- 部署：按 var.md 的工程脚本和部署 Skill 两个简短示例收集一段说明。工程脚本方式无需额外封装 Skill；CI/CD API 方式须由客户提前提供已上传并完成必要审核发布的部署 Skill，才可预检和初始化；本次统一批次将其绑定到测试与部署工程师并完成绑定的必要发布。读取实际脚本或 Skill 核实入口、参数及结果判定，复用已有信息，不把查询、超时、产物等内部实现细节逐项重复问客户。不默认示例命令、分支或参数真实有效。
- 数据库：按客户模板中的「数据库脚本」和「数据库配置」两部分收集。脚本部分说明目录、命名、全量结构维护、执行方式、检查及备份恢复约定；连接部分只收集数据库类型、版本、配置读取方式及配置项名称，不索取地址、账号、密码的实际值。推荐在 AutoWonder 平台统一配置环境变量及敏感值，无需为每个执行器环境手动配置。仅连库时，脚本约定标为不适用；明确不涉及数据库时两项均填不适用。未回答保持待确认，不按不适用处理，不在初始化时执行迁移。
- 其余变量：按真实声明解释、收集并填写；不适用要说明条件，缺值不能当作不适用。
- 仓库：将 [仓库填写字段](references/repository-intake.md) 合入同一份项目清单，收集地址、默认分支、职责和依赖关系，不另发一条收集消息；登记仓库、建立 Repo Map，并绑定所有成员，按角色分配 READ/WRITE。
- 部署分支：任何阶段均不收集 MR/PR 平台、策略或合并方式，正文也不询问这些内容。MR/PR 配置变量固定为「不创建 MR/PR，保留小队内部代码评审」。在项目反馈清单中收集每个参与测试环境部署的仓库及其明确的目标分支（例如 `dev`），不把仓库默认分支当作部署目标。缺分支时先补问。
- 将逐仓库目标分支和操作约定写入部署 SDLC 的「分支合并与部署准备」步骤（`qa_deploy_prepare`）中的「部署合并目标」变量。运行工单时，测试与部署工程师在评审和测试通过后，从远程最新部署目标分支合入当前工单已评审的开发分支提交，将合并结果普通推送到同一远程目标分支，核实远端提交后再继续部署。冲突沿用模板返工流程。分支保护、权限不足或推送失败时停止部署并报告，不强推，不改用其他分支，不自行创建 MR/PR。预检和初始化只写入约定，不执行 Git 合并或推送。

## 固定方案、协作图与执行结果

在 Chief 聊天正文简洁展示方案和结果，不发送 JSON 附件、原始工具输出或完整配置。完整资料已提交且统一预检通过时直接执行，不要求再次确认。

执行前以 `## 空间初始化方案` 展示：空间、小队、模板名称和版本；逐仓库分支及构建、测试、数据库、部署约定；角色权限、执行器客户端与模型；本次一次写入的配置范围。未核实项须先补齐，不当作已定配置。必要时展示下述协作图，不把图表审阅变成新的确认步骤。

协作图从所选模板的实际 SDLC、交接目标与本次配置差异生成，不能根据角色名推测连线。主线按入口到结束纵向排列，每行一个“数字人 · SDLC / 关键步骤”，行间用“↓”和简短条件；右列集中标注分支、返工去向、人工出口或结束条件。无 SDLC 的成员以“协作支持”行展示其职责，不画成自动交接节点。核实不到的交接标为待核实。

Chief 正文支持经白名单过滤的 HTML。流程图直接输出 HTML，不放进代码围栏，固定为两列表格 `<table>`，表头为“主线 ↓”和“分支与返工”，表体用 `<tr><td>…</td><td>…</td></tr>`，可用 `<strong>` 强调角色、`<br>` 换行。转义动态文本，保持单元格简短。使用平台默认样式，避免自定义 CSS、SVG、脚本、宽表和固定尺寸。当前界面不能渲染 HTML 时，用相同列名、行序和箭头的 Markdown 表格。

### 执行前先交代后续流程

调用 `initialize_workspace` 或恢复工具前，必须先发送客户可见的简洁说明，不能仅放在工具参数或思考过程里：

> 接下来我会一次完成模板、项目变量、默认执行器、仓库关系与权限、部署能力绑定及发布。若执行成功，空间配置初始化就完成了；请到「执行器」按平台启动指引启动小队成员的默认执行器，然后到「工单」新建任务，选择本次小队开始交付。如需检查运行准备，可启动后回到这里回复「执行器已上线」。若执行失败、仍在执行或结果不明确，请先不要进入下一步；若没有收到后续回复，发送「继续初始化」，我会查询并恢复本次批次，仅补未完成项，不会重新初始化。

恢复时按实际剩余项调整第一句，不暗示已完成项需要重做。执行前使用条件表达，不提前计为完成。已有执行器在线时复用实际状态，不要求重复启动。

原 MCP 调用返回后可在当前对话继续，必须补发 `## 空间初始化结果`，依次给出 **结果**、**已生效**、**下一步**。仅统一批次 `status=SUCCEEDED` 时说明：“空间配置已初始化完成。”并继续下文步骤，读取并提供本次全部默认执行器的实际启动命令。同时明确当前仅完成配置，尚未验证的在线状态、Git 访问、运行环境及真实构建、测试、部署不能宣称通过。部分失败写清已完成项、阻塞和原批次恢复动作；入队、执行中、无报错或消息结束均不等于成功。

## 初始化后：启动执行器并确认交付就绪

将启动、在线检查和交付就绪确认合并为一个后续步骤，不增加前述配置初始化的 2 步，也不把配置完成当作 READY。

统一初始化成功后，自动读取本次小队全部成员的默认执行器（以本次对象映射核对），并加入当前空间 Chief 在前置引导阶段使用的执行器。通过 `autowonder.list_agents`（遍历分页并核对返回的 `kind=PLATFORM`，必要时用 `autowonder.get_agent` 核实） 核实当前空间 Chief 的数字人身份，再通过 `autowonder.list_executors(agentId=Chief实际ID)` 定位前置引导使用的执行器，复用原执行器 ID 和已保存的启动配置。按执行器 ID 去重，完整清单包含 Chief 和本次小队全部成员的默认执行器。Chief 无法定位时先报告缺项，补齐后继续。对清单中的每个执行器，逐个调用 `autowonder.build_executor_launch_command` 获取平台生成的实际完整启动命令。只读取命令，不在服务端启动进程，不修改配置或重新生成令牌。名称、ID、命令必须对应，不手拼令牌、参数或使用示例替代实际命令。读取失败时明确列出缺失执行器，不声称命令已齐全。

将全部执行器的名称、ID和完整命令嵌入下方同一个可一键复制的本地 Agent 提示词，用空行和独立一行 `---` 分隔各执行器资料。保留命令和引号，不截断或省略，不再单独展示逐条终端启动方式。启动命令含连接凭据时仅在当前授权客户会话按需提供，提醒保存在本机受限文件，不提交仓库或转发公开渠道。

随后只展示 **统一后台管理**：将下方完整提示词复制给本地 Agent，生成一个支持 `start / stop / status` 的脚本。启动后终端立即返回，不用多个前台终端保持运行。

在该方式的操作说明中明确提示：「统一脚本包含 Chief 和本次小队全部成员的执行器启动命令。<span data-type="warning">运行 start 前，请先停止前置引导中手动启动的 Chief 等执行器进程，再由统一脚本启动，避免同一执行器重复连接。</span>若原进程在终端前台运行，可在对应终端按 Ctrl+C；后台运行时按原启动方式停止。保留平台中的执行器记录和连接凭据。」

上述 `<span data-type="warning">…</span>` 提醒必须在聊天正文中按原标记输出，平台将其渲染为加粗红色。将它放在可复制提示词代码块之前，代码块内继续保留完整的停止旧进程要求。

提供一个独立 text 代码块作为「复制给本地 Agent」的完整提示词。将下面占位说明替换为此次全部执行器的真实名称、ID和完整命令，直接嵌入同一代码块，不让客户再次拼接或复制命令；执行器之间以空行和横线分隔（作为资料分隔，不作为 shell 代码执行）：

> 下方清单包含 Chief 和本次小队全部成员的执行器。首次真实启动前，先将完整脚本和操作说明保存到本地，再核实并停止前置引导阶段手动启动的 Chief 等执行器进程，确认归属及原进程已退出后再执行统一脚本的 start，避免重复连接；保留平台执行器记录和连接凭据，不执行删除、注销或令牌重置。请根据下面 AutoWonder 执行器启动命令，先识别本机操作系统、当前运行环境、可用 Shell 和必要依赖，只为当前运行环境生成一个可独立使用的本地管理脚本，将全部执行器的名称、ID和启动命令直接写入同一个脚本，不另建或引用 commands 文件、配置文件或辅助脚本，不同时生成多个平台版本；运行时可以创建 PID 文件和日志。按平台选择：Linux/macOS 使用 Shell 脚本 `autowonder-executors.sh`，通过 `./autowonder-executors.sh start|stop|status` 调用；原生 Windows 使用 PowerShell 脚本 `autowonder-executors.ps1`，通过 `powershell.exe -NoProfile -File .\autowonder-executors.ps1 start|stop|status` 调用，若使用已安装的 PowerShell 7 则以 `pwsh` 调用。这里的 `start|stop|status` 表示三选一，交付时分别给出三条可直接执行的命令。区分 WSL 与原生 Windows，按执行器实际运行的环境选择，不要求 Windows 用户安装或切换到 Bash/WSL。缺少依赖或受执行策略限制时说明处理方式，不擅自安装软件或修改执行策略。保留原启动命令的可执行程序、包版本、全部参数及参数值；按所选 Shell 正确适配路径、引号和转义，确保传入进程的实际参数值不变，不把 POSIX Shell 语法直接交给 PowerShell。start 后台启动全部执行器，日志按执行器分别保存并立即返回终端，关闭调用终端后执行器仍运行；重复 start 不重复启动；stop 只停止本脚本管理的执行器及其子进程，不能使用按名称全局 kill 或 taskkill；status 按名称报告运行中、已停止或启动失败，并列出日志路径。使用独立 PID/进程标识和运行目录，核实进程归属，处理失效 PID，不能只凭 PID 文件存在判定存活，不能把旧 PID 指向的新进程误杀。若原启动命令已自行后台化，请适配其实际进程管理方式，不把已退出的启动器当作执行器。使用所选 Shell 的语法检查能力验证脚本；开发完成后按下方流程真实运行脚本进行验证，并说明脚本位置、适用平台及 start、stop、status 的使用方法。本地进程存活不等于平台已在线，启动后还需回到 AutoWonder 检查。
>
> 脚本生成与验证要求：
> - Linux/macOS 明确使用 Bash，兼容 macOS 自带的 Bash 3.2，使用 `#!/bin/bash`，避免关联数组、`mapfile` 等高版本特性。设置脚本可执行权限，并分别给出 `bash ./autowonder-executors.sh start`、`stop`、`status` 的完整调用命令。若用户以 `sh autowonder-executors.sh` 调用，脚本须在使用 Bash 专有语法前自动切换到 Bash 并保留原参数。

## 进度与恢复

通过 `autowonder.get_workspace_onboarding` 恢复已确认信息、对象映射和原批次，不重复回答或初始化。准备工具和预检只保存草稿/快照，不代表业务写入成功。权限或对象版本变化时重新预检，不能盲目重放。

新批次使用 `autowonder.get_workspace_initialization(runId)` 查询；失败直接调用 `autowonder.resume_workspace_initialization(runId)` 恢复同一批次，仅补未完成项，不追加行动计划。未知结果先查询，运行中的批次不另起批次。失败保留成果，不自动删除回滚，不重复创建、绑定或发布。只以统一批次 `SUCCEEDED` 判断配置完成，不以模板子批次成功代替。

历史确认计划在页面内支持自动续接；关页、续接失败或没有后续回复时，客户可回复「继续初始化」。不承诺关闭页面后仍会后台自动续接。收到继续请求后先恢复对象映射与原 runId，查询同一批次并按其状态恢复；确认统一批次 `SUCCEEDED` 后继续读取实际启动命令，不重新初始化。

旧 `get_harness_initialization`、`resume_harness_initialization`、`get_workspace_configuration`、`resume_workspace_configuration` 仅用于已存在历史批次的查询和恢复，遵循旧批次授权及快照语义；不得用于新初始化，不得退回 `initialize_harness` 加 `apply_workspace_configuration` 的分段写入流程。历史批次按实际配置缺口报告，不冒充统一批次成功；无法通过既有恢复能力完成时说明阻塞。服务端必要发布成功的结果作为依据，不发布后逐字段回读；后续就绪检查只查必要状态和证据。

## 模板维护

`harness-config.json` 是完整模板母版，顶层保持数组；目前一份模板。字段与引用校验由 `scripts/validate_config.py` 用于离线开发，Chief 不要求安装 Python。服务端必须执行等价校验，不能依赖模型或离线校验成功。

新增变量必须同时更新模板 variables 声明及必要的 var.md 引导。客户配置只写入实例快照，不回填母版。模板附带的 Skill 文件是待导入数据，不在初始化期间执行。
