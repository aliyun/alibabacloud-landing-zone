# 从多工单证据到可验证问题

## 建立分析表

每行代表一个工单中的一次步骤尝试，字段为 workitemId、dispatchId、agentId/实际版本、sdlcId/stepId、resumeMode、平台状态、运行错误、业务结论、输入指纹、产物引用、开始/结束、credits及来源/可用性、trace覆盖、证据定位。stepId 缺失时结合 step.started 事件、当前 turn 实际输入和产物对齐；只靠步骤名字猜测的映射标记 uncertain。

正式交付与旁路交互分开：COMMENT_INTERACTION、SIDE_INTERACTION、CANONICAL_INTERACTION 为交互；COMMENT_REWORK、RECOVERY、RETURNING_WORKER、null 属于正式交付；未知模式单列。最终 CANCELED 不抹去此前模型失败；SUCCEEDED 不等于产物验收 PASS。用户主动取消不自动归为配置故障。

耗时分为执行活跃、工具调用、等待/审批、排队、重试/恢复。父子 span、并发调用不直接求和作墙钟耗时；按区间并集或最高层实测区间统计，交叠不可明确时不汇总。等待长只能定位瓶颈，不能直接归因于指令。

credits 先检查 available/availability/source，再选唯一互斥层级。dispatch 总额用于总计；子调用明细用于分布，不能再加到总额。重试各独立 dispatch 可相加；同一 provider usage 在 turn 与 observation 中重复出现只能计一次。只有 dispatch 总额时，不按 token 或耗时比例臆造步骤成本。不同来源/单位分组；未上报、延迟上报单列。报告已知费用合计和覆盖分母，覆盖不足时不排名全体成本。不用 token 单价估算 credits。

## 两遍分析

第一遍从全部样本索引找重复信号，第二遍只把候选证据及正常对照装入分析上下文，其余正文留本地按 ID 检索。所有可用 trace 仍需完成采集或标记未完成。按工作类型、复杂度、成员/步骤和配置版本分组，避免把不同任务的天然差异当问题。

| 候选信号 | 必需的直接证据 | 常见反证 |
| --- | --- | --- |
| 输入/产物路径不匹配 | 实际步骤输入要求A、实际产出B、门禁错误、当前可修改字段；跨工单重复 | 产物未交付、路径被正确转换、当前配置已修复 |
| 门禁反复失败 | 同一校验失败明细和满足业务要求的实际产物；简单校验可替代且质量等价 | 门禁正确发现真实缺陷，不能删除 |
| 指令冲突/过宽 | 两个实际加载要求的冲突片段，模型因此反复切换/失败的输入输出链 | 管理页面文本未加载；任务确需探索 |
| 失效记忆 | 实际被读的记忆内容/版本与当前权威事实矛盾，并引出错误操作 | 只是未采用的历史内容；记忆已更新 |
| 重复探索/读取/测试 | 相同输入指纹、无新提交/环境/要求、重复命令及等价输出；可复用产物可访问 | 独立评审职责、提交变化、测试失败复核、环境隔离 |
| 环境或能力配置缺失 | 缺引用/错误绑定与实际失败对应；可用的配置修正有明确路径 | 供应商限流/500、平台恢复缺陷或权限不足 |
| Skill 方法错误 | 实际加载 Skill 的具体指令、重复错误行为与修正方法 | 未加载该 Skill 或错误来自别处 |
| SDLC 交接模糊 | 多工单重复追问/重新发现同一事实，当前输入遗漏明确必要信息 | 接收者没有权限或产物不可用属于平台问题 |

不要自动把 npm ci、HEAD校验、全量测试、review 或恢复判定为浪费。先确认工作区隔离、依赖缓存、职责要求和实际增量。不要用“减少提示词”替代明确的冲突定位。

## 证据门槛和 review

每个候选必须填：可比较工单数 N、同因工单数 n、不同案例定位、正常对照或缺失原因、当时配置证据、当前配置是否仍适用、因果链、用户可改的具体字段、反证和质量风险。

仅当 n≥2 且来自不同工单、因果可验证、当前配置仍存在同一问题、用户能通过配置维护解决时，进入“可行动”。样本整体少于5时注明低覆盖，不下整体趋势结论。两个同文错误但不同原因不合并；同工单五次重试仍只计1。n/N 仅描述本次可比较样本，不是平台总体发生率。

若当前配置与执行时不同：先检查问题是否已经修复，无法确认就列“待验证”，不再建议相同修改。没有历史内容但有当前明确矛盾可列配置审查观察，不能虚构它导致历史费用。

独立做一次反向 review（有独立 reviewer 能力时可用，没有则逐项反证）：
1. 删除证据后建议是否仍像泛泛最佳实践？若是，补证或剔除。
2. 每个案例是否真正加载了相关要求？能否用配置以外因素解释？
3. 修改是否在用户可维护范围，是否保留业务目标与验收质量？
4. 改动后的当前执行者能否仅凭本次输入执行？有没有跨文件/未来步骤的上帝视角？
5. gatePolicy 是否仍采用平台已有常见校验，是否增加新故障面？
6. 验证能否判定修改失败并回滚？节省是否只是猜测？

分类只用：可行动、待验证、已修复、平台/执行器/供应商问题、正常必要工作。只有可行动生成 diff。没有可行动项时，清楚说“本次样本未发现有充分证据、可由配置维护解决的通用优化项”，列覆盖范围和缺口即可。

## 指令改写示例（示意，不是真实工单证据）

若多个独立工单证明报告生成位置与校验路径不一致，报告里可以写“修改步骤的 instructionMd 与 gatePolicyJson”。下发文字写：

> 完成测试后，将测试命令、退出码、失败项、产物路径和未验证范围写入 `artifacts/output/evidence/test-report.md`。确认文件存在且非空，再提交该路径作为验收证据。测试失败时保留失败记录并给出修复清单。

不写“按 soul.md 的要求，参考下一步完成交接”。若只是正常质量失败，不改门槛；若证据仅一例，上述示例也不能直接套用。
