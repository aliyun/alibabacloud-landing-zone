# 历史 checkpoint 的目录引用兼容

## 问题与范围

部分旧 Runtime 在 checkpoint 的 `reference_only` 发布记录中写入了执行目录
`t/<tenant>/workitem/<workitem>/dispatch/<source>/`，同时省略了文件正文。
新版 Runtime 要求引用指向具体对象，因此即使文件已成功上传，恢复仍会报
`ARTIFACT_REFERENCE_INVALID`。工单 55411、来源执行 13378 的两份历史 checkpoint
属于这一情况。

本修复只改变服务端生成恢复候选的过程。无需升级 Runtime、修改协议、迁移数据库、
调整 Redis 或更改调度状态机。正常新 checkpoint 仍使用原 URL、原 SHA 和原序号。

## 兼容规则

1. 校验原归档的长度、SHA、来源 dispatch 和 checkpoint 序号。
2. 只识别 v2 checkpoint 发布清单中与来源执行目录完全相同的旧 `reference_only` 引用。
3. 在同租户、同工单、同来源执行的 WORKITEM 产物记录中查找对应文件；验证对象路径、
   实际字节长度和 SHA。缺失、冲突或校验失败时不猜测。
4. 仅将 accepted/attempt 发布清单中的旧目录引用替换为已验证的具体对象引用。
   步骤状态、原完成时间、receipt 身份、仓库内容及文件属性不变。
5. 将结果写入原对象旁的 `.compat-exact-ref-v1.tar.gz` 副本，使用现有候选 URL/SHA
   字段下发。原对象及数据库中的 durable receipt 保持不变；顶层 URL/SHA 与首个候选一致。

副本内容确定，已有同名对象内容不一致时不覆盖。原 checkpoint 被保留策略淘汰时，
同时清理其兼容副本。正常归档只扫描必要元数据，不把无关文件正文全部保存在内存中。

不能证明可修复时保留原候选，由 Runtime 继续原有候选回退和错误处理；**不会清空恢复
状态并伪装成新任务执行**。含未完成 publication journal 的归档不在此次窄范围修复内。
归档、展开大小、成员数量、JSON 和单产物大小均有限制，拒绝不安全路径、链接和重复成员。

## 部署与恢复

部署服务端即可在下一次恢复派发时按需兼容旧 checkpoint；没有批量改写线上数据的步骤。
已经 FAILED 的执行不会仅因部署自动复活，应通过现有“继续执行”入口创建恢复执行。
仍然排队的恢复执行在正常派发时自动使用兼容候选。

真实文件已丢失或内容不匹配的情况不会被本修复掩盖，需要按原有错误处理。
