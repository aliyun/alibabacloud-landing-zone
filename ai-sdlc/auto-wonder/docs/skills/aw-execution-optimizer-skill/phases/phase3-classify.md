# Phase 3: 问题归类与归因

## 四类归属

| 类别 | 判据 | 典型问题 |
|---|---|---|
| **平台** | 平台执行器代码/机制缺陷;换客户仍存在 | 残留进程/事件缺失/契约不完备 |
| **SDLC** | 步骤指令的措辞/结构/缺失导致浪费 | 不给预算/反事实禁令/散文输出 |
| **Agent 定义** | Agent.md/Soul.md 的约束或声明不足 | 无正向规模界/重复 SDLC |
| **环境** | 执行机器的配置/工具链缺失 | 浏览器未预装/npm 双源/端口冲突 |

## 归因原则

1. 每个问题必须有**实证**(时间戳 + 命令 + 行为 + 结果),不允许"可能有问题"
2. 按**是否已造成真实后果**排优先级,不按理论严重程度
3. 平台问题**只报告不修** — 这是平台团队的事;SDLC/Agent 问题**给方案**
4. 环境问题**报告 + 建议配置**,不假设用户环境
5. **逐条结论回查(硬性要求)** — 进入 Phase 4 之前,把得出的**每一条**问题与结论挨个回顾日志复核:重新打开对应的执行日志/事件数据,确认每条都能落到具体的时间戳、命令或 agent 原话上,因果链条每一环都有数据支撑;**任何一条复核不通过(证据不足或存在反例)就降级标注或剔除**,不允许带着未经回查的结论进入优化方案。实证案例:"读 contract 导致 72s WAIT"的归因在回查中被证伪——另一个 dispatch 同样全文读取却无 WAIT 长尾,未回查就会把错误禁令写进指令
