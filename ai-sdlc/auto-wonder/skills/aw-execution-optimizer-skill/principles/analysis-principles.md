# 分析原则

## 1. 不凭代码推断,必须有执行数据佐证
每个结论必须指向:
- 具体的 seq 编号或时间戳
- 具体的命令内容或 agent 原话
- 可复现的行为模式(不是一次偶然)

## 2. 区分"模型行为波动"和"结构性问题"
- 同一步骤在不同工单上表现一致 → 结构性问题(SDLC/Agent 配置)
- 同一步骤在不同工单上波动大 → 模型行为,不可归因

## 3. 区分"agent 选型差异"和"SDLC 引导错误"
- agent 自选了一个贵的方案(如下载 chromium)但 SDLC 没说要 → agent 选型
- SDLC 无条件触发了一个贵的动作且不给降级 → SDLC 引导错误

## 4. 平台事实 vs 业务指令
- 平台只声明事实(什么存在/什么不存在/什么会发生)
- SDLC 给业务取值(用什么工具/跑什么命令/输出什么格式)
- 两者不能混:平台不该指导业务行为,SDLC 不该替平台声明环境

## 5. 每条建议必须可验证
不说"优化 SDLC 可以提升效率",说:
- "改完后不应出现 `npx playwright install` 命令"
- "400164 的 tool_use 应 ≤ 25 次"
- "CR 400170 不应出现 vitest/mvn test 命令"

## 6. 不能用单次重跑的总墙钟验证优化效果

**这是三轮实战最重要的方法论结论之一。**

为什么:
- WAIT + STREAM = ~75% 的时间是模型行为,受采样噪声影响
- WAIT 层因底层 provider 不透出 token 用量而永久不可归因
- 单次重跑的总时长会被一笔大的 agent 选型差异(如下载 chromium 5m29.6s)主宰

正确的验证方法:
1. **看二元事件信号** — "出现/不出现某命令"比"总时长降了 X%"更可信
2. **看 TOOL 段的具体命令** — 不依赖 WAIT/STREAM 的变化
3. **看行为模式是否消失** — "子代理不再派出" / "不再出现 playwright install" / "evidenceRefs 全部正确"

我们实际用的四个验收信号:
- artifact.sealed 事件出现(步骤边界可观测)
- 重做推理原文消失(grep 基线关键词)
- evidenceRefs 格式正确(非 None / 非错误字段名)
- 拼错字段被 400 拒绝或一次写对

## 7. STREAM 可间接压缩——不是固定成本

归因文档原判断"平台单独动不了 STREAM(48.5%)"被第二轮数据部分推翻:
- 全局 STREAM 降了 12m39.1s(48.5% → 36.8%),是全局最大的单项变化
- 机制:STREAM 与"要叙述多少动作"强耦合;减少重复工作 → 减少叙述 → STREAM 下降

在分析和优化中的含义:
- 不要因为某步 STREAM 占 60% 就认为"改不了"
- 检查那个 STREAM 是否在叙述不必要的工作(如重做/探测/枚举)
- 消除那些工作后 STREAM 自然跟着降

## 8. 约束宾语必须覆盖 agent 会走的全部字面合规路径

当约束被遵守但仍然浪费时,问题不在 agent 不听话,在宾语太窄。agent 是字面遵守者 —— "不运行测试"不能阻止"运行编译";"不结束回合去等"不能阻止"后台+轮询";"不再复跑基线"不能阻止"复跑当前分支上那几个失败用例"。

方法:
1. 观测 agent 实际做了什么(从 bash.call 逐条看)
2. 对每条非交付动作问:现有约束的哪个词挡住它了?
3. 如果答案是"没有词挡住它"→ 约束欠定,需要扩宾语
4. 扩宾语时**显式列出被禁的命令名或工具参数**,堵住"字面合规但语义违反"的路

实证:
- "不运行测试" → 没挡住 `mvn -DskipTests compile` → 改为"不运行 mvn compile / mvn test / ..." → 0 次 compile(−570s)
- "不结束回合去等通知" → 没挡住 `run_in_background` + 轮询 → 点名"不用后台任务模式(run_in_background)" → 0 次 bg(−107s)
- "仅当结论缺失或存疑时才独立复跑基线" → 没挡住"复跑当前分支上那些用例" → 改为"存量失败用例不再复跑" → 定向复跑只剩改动路径

**与原则 5(可验证)的关系:** 宾语扩了之后,验证信号也要跟着扩。验收时不能只看"agent 没跑测试",还要看"agent 也没跑编译"。

## 9. 效率优化必须附带质量不降的实证

单看时间降了不够,速度和质量是一对需要同时度量的维度。优化报告完成后(Phase 5 应用之后),如果用户提供了重跑后的新日志,应进入 Phase 6(质量验证)做三维度前后对照,确认交付质量未被压缩。

这一条的核心是:**省下来的时间,必须全部来自非交付性活动**(重复编译、环境搏斗、后台轮询、补救回合重定向、STREAM 叙述减少)。如果实测发现某个交付维度回退了(如测试用例数减少、评论信息缺失、验收标准未满足),该优化点必须回退。

实证:
- 50309→50314 时间 −52.6%(53.1m→25.1m)
- 评论:持平或更好(50314 有独立自测评论,50309 没有)
- Evidence:0 文件 → 7 文件(显著提升)
- 代码:8 文件/108 条测试/12 条验收标准全一致
- **结论:省的 28 分钟全部来自编译(9.5m)+esbuild(6.0m)+轮询(2.5m)+STREAM 间接压缩,零交付质量损失**
