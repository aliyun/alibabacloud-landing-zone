# SDLC 坏模式检测器(8 特征)

逐步骤检查 instructionMd,检测以下特征:

## 1. 触发动作不给预算
**检测:** 指令含动作动词(如"运行/执行/搭建/验收/统计")但:
- 无 `budget.notes`
- 指令中无【预算约束】段
- 无时间/规模/轮次上限描述

**严重程度:** 高 — 实测证明同一句话在两轮间成本差 9 倍。

---

## 2. 要求度量不给口径
**检测:** 指令中出现"统计/覆盖率/达标/合格"等词,但:
- 未指定用什么工具
- 未指定计算方法
- 未指定阈值或"未配置则标注"的降级

**实证:** "统计增量覆盖率"8 字 → 两轮各造一套(Perl 解 jacoco vs v8 coverage+git diff),数字不可比。

---

## 3. 要求能力不验证能力
**检测:** 指令点名某工具/MCP(如"用 code MCP 创建 MR"/"使用 aone-mix"),但:
- `skills.json` 中未声明该 MCP
- 或平台 `## Available Capabilities` 清单中没有

**注:** 如果平台已声明能力清单(v0.2.135+),这个检测的意义降低(agent 会看清单)。

---

## 4. 禁止 agent 承认现实
**检测:** 指令中含:
- "不能直接判断缺少..."
- "不得跳过..."(针对客观不存在的能力)
- "必须尝试..."(针对明确不可用的工具)

**实证:** "不能直接判断缺少部署能力" → 动作 6→24,+1m59.1s。

---

## 5. 散文式输出要求
**检测:** 汇报/交接类步骤的指令中:
- 无代码块包裹的模板
- 无固定小节标题
- 无"不得自由发挥"/"无内容填「无」"类约束

**对照:** 有硬模板的步骤输出体量是散文式的 1/4(实测:752 vs 2944 字符)。

---

## 6. 替平台兜能力缺口
**检测:** 指令中:
- 大段(>200 字符)描述"如果工具不可用则..."的降级路径
- 含写死的 URL 模板(如仓库创建 MR 链接)
- 含多个仓库各自的 URL 格式

**注:** 平台 v0.2.135+ 已通过 `## Available Capabilities` 声明能力可用性,这类降级散文应精简。

---

## 7. 不声明可复用上游产出
**检测:** 步骤指令中:
- 无"复用前步/引用上游/不得重复"类表述
- 上一步有 evidence 产出(从 artifact.sealed 事件知道)但当前步可能重做

**实证:** CR 重跑 dev 已跑的 vitest(34.73s),虽然上游日志在清单中。

---

## 8. 长命令步骤的回合约束缺失或写反

这一条有**两个方向**都要查,漏了任何一个方向都会掉进另一个坑。

**检测 8a(缺失):** 步骤指令要求跑测试/构建/依赖安装,或要求"等待"外部系统结果(部署、流水线、变更单),即单条动作可能耗时 >1 分钟,但指令中没有任何"要在当前回合内拿到结果"的表述。

**检测 8b(写反 / 过度纠正):** 指令里出现下列任一表述 —— 这会把并发一起禁掉,拿失败换降速:
- "不要放到后台" / "禁止后台执行" / "不得使用 `&`" / "禁止 nohup"(**没有**同时说明"可以并行发起")
- "逐个执行" / "串行执行" / "一次只跑一个套件"
- 只说"前台执行"而不区分"并行发起"与"结束回合去等"

**严重程度:** 8a 高(整个 attempt 作废并原地重来);8b 中(不会失败,但把可并行的墙钟拉长成累加)。

**这两个坑源自同一个混淆 —— 两个正交维度被当成一个:**

| 维度 | 含义 | 决定 |
|---|---|---|
| 并行 / 串行 | 是否同时发起多个命令 | **速度** |
| 回合内等 / 结束回合等 | 谁来等命令结束 | **成败** |

致命的只有"结束回合去等"。`cmd1 & cmd2 & wait` 写在一条命令里用了 `&`,但从回合视角看完全是前台的(整条命令阻塞到 `wait` 返回),它**既并行又安全**。所以约束必须精确打在回合边界上,不要打在 `&` 这个字符上。

**实测对照(同一工单 50245):** attempt 3 在**一个回合内并发发起三个前台调用**,17 毫秒内全部发出,总墙钟 119.6 秒:

```
05:56:58.621 CALL  curl(进度事件)     → 05:58:58.005 RESULT 119383ms
05:56:58.633 CALL  mvn -o test        → 05:58:58.106 RESULT 119473ms
05:56:58.638 CALL  npm ci + vitest    → 05:58:58.207 RESULT 119569ms
```

串行跑同样三件事要约 358 秒。**前台没有牺牲任何并发度** —— 失败的 attempt 1/2 和成功的 attempt 3 在"并行"这个维度上完全一样,区别只在"谁来等"。

**机制:** agent 结束一个回合时若始终没 POST 过 `completion_requested`,runtime 会免费补一个回合;补的这个回合又空手结束才记 `step.failed` reason=`missing completion request`,继而 `session.failed` → `dispatch.failed`。注意这个补救额度是**按 gate 轮次**给的,不是每个步骤一次 —— 提交后被 gate 驳回会回到新一轮并重新拿到额度。回合内发的 `progress` 事件不算数:只有 `completion_requested` 才会生成 completion request。没有任何机制会在后台任务完成时唤醒 agent;dispatch 结束时 `workspace.processes_reaped` 终止仍在跑的子进程,下一次重试拿到全新的 `attempt-N/workspace`,依赖安装与测试从零重跑 —— 同一段开销被反复重付,直到某一轮凑巧改成前台执行。

**实证:** 工单 50245 QA 步骤 400173(mvn test ~2min + npm ci + vitest)。attempt 1、attempt 2 都把两个套件放后台后结束回合等通知 → 两次都是 `missing completion request`,checklist 四项全 `false`。两次失败的步骤墙钟合计约 4.5 分钟(3m10s + 1m21s),整条 QA 链路从 13:41 拖到 13:56 才拿到结果。attempt 3 改为前台执行(mvn 实测 119s)一次通过。三次派发的被测代码完全一样。

**修法:** 一句话就够。**直接抄下面这个模板**,加在该步已有的【】约束块旁边(通常放在【预算约束】前面):

```
【执行方式】测试、构建、依赖安装等长命令要在当前回合内拿到结果。鼓励并行发起(并行工具调用,或 `cmd1 & cmd2 & wait` 合成一条命令),但不要发起后就结束回合去等通知。
```

把"测试、构建、依赖安装"替换成该步真实的长动作即可,其余原样保留。三个成分都是必需的,少一个就退化成 8a 或 8b:

| 成分 | 作用 | 删掉会怎样 |
|---|---|---|
| "要在当前回合内拿到结果" | 正向要求,打在回合边界上 | 退化成 8a,原问题复现 |
| "鼓励并行发起(…)" | 明确保住并发度,并给出具体写法 | 退化成 8b,agent 保守解读改成串行 |
| "不要发起后就结束回合去等通知" | 精确指出被禁的到底是什么行为 | agent 不知道边界在哪 |

**反面写法,不要用:**

| 别这么写 | 问题 |
|---|---|
| `不要放到后台` / `禁止使用 &` | 打在字符上而非回合边界上,顺手禁掉 `& wait` 并行 |
| `逐个执行测试套件` | 直接把并发写死成串行 |
| `前台执行长命令` | 没说可以并行,保守 agent 会串行化 |
| `…否则本步判失败` | 制造紧迫感却无退路,见下方第 2 条 |

**不要写得比这个模板更多。** 我们在 AW 自身的 40016/40014 上试过加长版(含回合预算、失败后果、进程回收、超时建议),复盘后全部删回一句话,原因是长版本引入了两个比原问题更糟的后果:

1. **写出"你还有一次补救回合"= 邀请 agent 规划着用这个余量**,正好是本特征要消除的行为。补救额度是 runtime 的内部实现(而且是按 gate 轮次给的,不是每步一次),不该出现在指令里。
2. **只给紧迫感、不给退路会诱发假 PASS。** 写"再不提交 `completion_requested` 就判失败"却不写"如实报阻塞是可接受结果",agent 的最优自保策略变成"先把 completion 发出去"。若该步 gate 只校验 `evidence/` 非空(400173 就是这样),假提交会直接过 gate —— 一次可见的失败被换成一次静默的假 PASS 并交接给下游。

所以:**SDLC 侧只留正向的执行方式要求,把回合语义、失败判定、进程回收都交给平台 contract 的 `## Turn Boundary` 承担。** 指令里不提失败后果,就不会有造假压力。

等待外部系统(部署/流水线)结果的步骤是另一类问题,不要套用这句 —— 部署耗时通常超出单个回合,给轮询上限和"未达终态"降级路径才是对的,而具体上限取决于各团队流水线实际耗时,不要凭猜写死。

**注:** 平台侧已在 contract 中补 `## Turn Boundary` 段,声明前台执行要求、"跑不完就缩范围"和进程会被回收 —— 同样刻意不披露补救额度。判断执行器是否已带这个修复:看 `bootstrap/runtime-contract.md` 里有没有 `## Turn Boundary`。有则这个检测降为双保险,SDLC 侧仍建议保留:等待外部结果的轮询上限与降级路径是步骤专属的,平台的通用契约管不了。

---

## 9. 编码步搭载无消费方的验证命令

**检测:** 编码类步骤(指令含"编码/实现/编写"且 **不** 含"测试/验证/自测")的 bash.call 中出现:
- `mvn compile` / `mvn -DskipTests compile` / `mvn test-compile`
- `npm run build` / `npx tsc --noEmit` / `go build`
- 且该步的预算约束宾语只覆盖"测试"(如"不运行测试"),没有覆盖"编译/构建"

**判据:** 下游步骤(自测/交付)是否独立跑了相同或更强的验证命令?如果是 → 编码步的验证无消费方,纯浪费。另外检查 CR 的 Scale 是否写了"仅累计 diff" —— 如果是,则逐 commit 可编译这个性质无人消费。

**严重程度:** 高 — 实测每次 `mvn compile test-compile` 含 git hooks 约 120s,5 次 = 570.1s(9.5m),占全链路 13.8%。

**实证案例:** 工单 50309 DEV 400165:5×`mvn -DskipTests compile test-compile`(每次 ~120s,含 cp/python3 改文件 + compile + git commit + hooks×4)。约束写的是"本步只做编码和编写测试用例,不运行测试",agent 用 `-DskipTests` 字面合规但仍在每次 commit 前跑编译验证。改为"不运行编译和测试"并显式列出被禁命令名后,50314 同步骤 **0 次 compile**,墙钟 23.2m → 12.4m(−46.5%)。

**修法:** 约束宾语必须覆盖所有非交付性验证动作。模式:

```
【预算约束】本步只做文件编辑和 git commit;不运行 mvn compile / mvn test / npm run build / vitest / go build / go test 或其他编译测试命令;完成全部编码后分少量有意义的 commit(按逻辑单元,不逐文件 commit)。
```

显式列出被禁命令名是必要的 —— 只写"不编译"时 agent 可能认为 `tsc --noEmit`(类型检查)不算编译。列了就没有灰色地带。
